## 2026-08-14 — Bug fix: Permission Builder silently over-granted custom modules to every role

Fixed a privilege-escalation bug reported for the Planning Officer role: revoking access to a module worked, but the role would also end up with access to unrelated modules (including Main Controls) it was never granted.

- Root cause: `fetchPermissionsData()` in `assets/js/rolespermission/permissions/api.js` had a block ("Automatically grant ALL action permissions for newly created/custom modules across roles") that unconditionally injected every action, for every role, into `window.savedPermissions` whenever a module/resource was still flagged `is_custom` — i.e. a module/resource created via Module/Resource Management whose client-generated local ID never reconciled with its real database ID (falls back to `Date.now()` when the create response doesn't echo the real ID back, which then never matches on a later sync). Because `saveChanges()` POSTs the entire `currentPermissions[roleId]` map as a full replace (not a diff), saving *any* unrelated change for a role also persisted this silently-injected full grant to the database.
- Fix: removed the auto-grant block. New/unsynced modules now start with zero granted permissions for every role, same as any DB-synced resource — an admin must explicitly check them per role in the Permission Builder. The separate `is_custom` bypass in `ui.js` (`isModuleAllowedForDepartment`/`isResourceGrantedToCurrentUser`) is unrelated and untouched — it only controls whether the *currently logged-in admin* can see/toggle a module they just created, not what gets granted to other roles.
- Bumped `ASSET_VERSION` in `assets/js/app.js` per convention.
- **Follow-up needed**: this only stops the bug going forward. Any role (e.g. Planning Officer) that had permissions saved while the bug was active may already carry unintended real grants in the database — review and re-save affected roles in the Permission Builder to clear them.
